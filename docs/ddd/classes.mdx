# Runtime classes

`JIT.class` is constructor-first by default:

```ts
const User = JIT.class(
  JIT.object({
    id: JIT.string().default(() => crypto.randomUUID()),
    name: JIT.string(),
  }),
);

const user = new User({ name: "Ada" });
```

No `create` or `hydrate` alias exists on that class. Opting into factories closes
direct construction, so the Runtime Type still has one canonical boundary:

```ts
const User = JIT.class(UserSchema).factories({
  create: "make",
  hydrate: "restore",
});

const created = User.make({ name: "Ada" });
const restored = User.restore({ id: "u_1", name: "Ada" });
// new User(...) // type error; runtime also rejects it
```

The create factory accepts `JIT.Input<typeof Schema>` and resolves creation
defaults. Hydration accepts complete `JIT.Hydrate<typeof Schema>` state and
never regenerates missing persisted values. Both preserve the subclass type
when called on a derived class.

Use `.factories({ create, hydrate })` to enter factory mode and configure its
names. At least one factory must remain enabled. Use `.accessors(...)` for
visibility/storage policy and `.extends(...)` for capabilities such as
`JIT.class.equals`, `hashCode`, `diff`, `clone` and `with`, and for
application-owned methods. Compiled helpers and extension methods live on the
prototype, never per instance.

Custom methods and getters preserve their descriptors and receive the current
instance as a fully contextual `this`:

```ts
const User = JIT.class(UserSchema)
  .extends(JIT.class.equals)
  .extends({
    displayName() {
      return this.name;
    },
    sameAs(other: unknown) {
      return this.equals(other);
    },
    get initial() {
      return this.name[0];
    },
  });
```

Extension names cannot shadow schema accessors, factories, the constructor or
an installed capability. Runtime installation uses the prototype directly;
there is no extension registry or dispatcher, and two instances share the
same function.

`.extends()` is stateful: each call sees the fields, built-in members,
capabilities, and custom members accumulated by previous calls. Existing
members are never silently replaced. Use `JIT.overwrite(...)` on the specific
member when replacement is intentional:

```ts
const NamedUser = User.extends({
  label() {
    return this.name;
  },
});

const UpperUser = NamedUser.extends({
  label: JIT.overwrite(function label() {
    return this.name.toUpperCase();
  }),
});
```

The marker is declaration-only. It disappears before class compilation, so
the generated method has no overwrite check or dispatch. Overwriting a
managed lifecycle field is also declaration-only and the final schema is
rechecked against its capability contract.

Built-in extensions are reconstructive AOT capabilities. Arbitrary JavaScript
methods are runtime bindings, not source artifacts: standalone AOT generation
skips the complete class with a `class.extends` reason. JIT never serializes a
method through `Function#toString`, because moving source would lose its lexical
environment and could silently change behavior. A future AOT form requires a
declarative method IR or an explicit external-module binding contract.

`pnpm bench:validate` measures a custom prototype call at 5.76 ns against
5.44 ns for the equivalent handwritten class method (Node 22.17.1, Ryzen 7
5800H), with about 6.1 sampled bytes per call for both. There is no extension
dispatcher. No custom-method AOT number is reported because that artifact is
explicitly unsupported rather than unsafely reconstructed; built-in
capabilities retain their normal runtime/AOT benchmarks.

`JIT.class.abstract(schema)` is an abstract constructor-first base. Configure
factories explicitly when its concrete subclasses should be factory-built.
