# Entities

Entities are compared by stable identity rather than by every field:

```ts
const UserBase = JIT.ddd.abstract.entity(
  JIT.object({ id: JIT.string().readonly(), name: JIT.string() }),
  { id: "id" },
);

class User extends UserBase {}

const before = User.hydrate({ id: "u_1", name: "Ada" });
const after = User.hydrate({ id: "u_1", name: "Ada Lovelace" });
before.sameIdentity(after); // true
```

`JIT.ddd.entity(...)` creates a concrete factory-first Runtime Type. Use
`JIT.ddd.abstract.entity(...)` when application code must own the concrete
subclass. The abstract base rejects `create()`/`hydrate()` until invoked through
a subclass. `create()` is for new state; `hydrate()` is for complete persisted
state. The identity field must be declared by the schema and remains part of
the ordinary validation and transport representation.

An explicit `{ id }` remains available and always wins. It may be omitted only when exactly one object field is a `JIT.ddd.uniqueIdentifier()` Runtime Type:

```ts
const UserId = JIT.ddd.uniqueIdentifier();
const UserBase = JIT.ddd.abstract.entity(
  JIT.object({ id: UserId, name: JIT.string() }),
);

class User extends UserBase {}

const user = User.create({ name: "Ada" });
user.id.value; // generated UUID
```

Zero candidates and multiple identifier candidates are rejected unless the identity field is explicit. This avoids guessing when an entity contains both its own ID and another aggregate's ID.

Lifecycle capabilities may add their managed state structurally, before the
entity is compiled:

```ts
const AuditedUser = JIT.ddd
  .entity(JIT.object({ id: UserId, name: JIT.string() }))
  .extends(JIT.ddd.timestamps(), JIT.ddd.softDelete(), JIT.ddd.versioned());

const user = AuditedUser.create({ name: "Ada" });
user.createdAt; // Date
user.updatedAt; // Date | null, initially null
user.deletedAt; // Date | null, initially null
user.version; // 0
```

`createdAt`, `updatedAt`, `deletedAt`, and `version` are required persisted
state for `hydrate()` and are excluded from ordinary user updates. Existing
canonical fields are reused when compatible; incompatible fields fail during
declaration.
