## Runtime classes

`JIT.class(schema)` generates a constructor-first class whose constructor
assigns fields in schema order. It has no default factory aliases.

```ts
const UserSchema = JIT.object({
  id: JIT.string().default("generated"),
  name: JIT.string().min(2),
});

const User = JIT.class(UserSchema).extends(JIT.class.equals, JIT.class.with);

const ada = new User({ name: "Ada" });
const grace = ada.with({ name: "Grace" });

ada.equals(grace); // false
```

Capabilities are explicit, installed once on the prototype, and reuse the
structural compilers: `equals`, `hashCode`, `diff`, `clone`, `with`, and
`identity("field")`. `with` accepts the schema-derived update patch type; readonly
schema fields cannot be patched and are preserved by the compiled update.

## Extensions

`.extends()` takes built-in capabilities, application-owned methods, or both.
Everything it installs lives on the prototype: one function shared by every
instance, reached the way a hand-written class method is reached. There is no
dispatcher between the call and the body.

```ts
const Member = JIT.class(UserSchema)
  .extends(JIT.class.equals, JIT.class.clone)
  .extends({
    displayName() {
      return this.name.toUpperCase();
    },
    sameAs(other: unknown) {
      return this.equals(other);
    },
    get initial() {
      return this.name[0];
    },
  });

const member = new Member({ name: "Ada" });
member.displayName(); // "ADA"
member.initial; // "A"
```

`this` is the instance the class already has — its schema fields and the
capabilities installed before, including ones named in the same call:

```ts
const Bucketed = JIT.class(UserSchema).extends(JIT.class.hashCode, {
  bucket() {
    return this.hashCode() % 8;
  },
});
```

Property descriptors are preserved, so a getter stays a getter. Generic methods
keep their inference, and the methods become part of the instance type.

A name that already means something is refused, in the types and at run time:
a schema field, a factory, `constructor`, or a capability installed earlier. A
silent shadow would look like it worked and change what the class is. Use the
explicit `JIT.overwrite(value)` marker when replacement is intentional:

```ts
JIT.class(UserSchema).extends({ name() {} });
// JITError: Class extension "name" would shadow an existing member; rename it
```

## Overwriting members

`JIT.overwrite(value)` replaces exactly one member that already exists. It is
resolved while the class definition is accumulated and disappears before
runtime or AOT compilation, so generated methods have no marker checks or
dispatch:

```ts
const Named = JIT.class(UserSchema).extends({
  label() {
    return this.name;
  },
});

const Upper = Named.extends({
  label: JIT.overwrite(function label() {
    return this.name.toUpperCase();
  }),
});
```

The same marker can replace a built-in method, an earlier extension, or a
managed lifecycle field. A missing target is an error, and a field overwrite
is checked again against any capability that still owns it. Arbitrary
application functions remain runtime bindings and make standalone AOT skip
the complete class with an explicit reason.

## Accessors

`accessors()` rematerializes a class with its configured backing layout. Private
fields use JavaScript `#` slots; getters and setters are emitted directly on the
prototype, including in AOT output. Per-field settings override `default`.

```ts
const Account = JIT.class(
  JIT.object({ id: JIT.string(), passwordHash: JIT.string() }),
).accessors({
  default: { field: "private", get: "public", set: "protected" },
  fields: {
    id: { set: false },
    passwordHash: { get: "protected", set: "protected" },
  },
});

const account = new Account({ id: "a_1", passwordHash: "..." });
account.id; // "a_1"
```

## Construction factories

Calling `.factories(...)` changes the class to factory-only construction.
Creation resolves defaults; hydration requires complete persisted state and
does not apply creation defaults. The configured names are the only aliases:

```ts
const User = JIT.class(UserSchema).factories({
  create: "make",
  hydrate: "restore",
});

User.make({ name: "Ada" });
User.restore({ id: "u_1", name: "Ada" });
// new User(...) is rejected by TypeScript and at runtime.
```

Runtime and AOT preserve the same configured names.

Use `.construction("factory")` when canonical factory names are sufficient,
or `.construction("constructor")` to opt a DDD Runtime Type into direct
construction. The switch replaces the current boundary; it never exposes
`new` and factories together, and it may be declared only once.

## DDD factories

The domain-oriented factories live under `JIT.ddd`: `JIT.ddd.valueObject`,
`JIT.ddd.entity`, `JIT.ddd.aggregateRoot`, and `JIT.ddd.domainEvent`. They are
presets over the same runtime-class machinery, grouped because they are a
vocabulary — someone reaching for an entity is not shopping among the schema
factories.

`JIT.class` stays at the top level. It is the primitive the presets configure,
and DTOs, JSON pipelines and AOT class artifacts build on it without any
domain meaning attached.

```ts
const UserBase = JIT.ddd.abstract.entity(
  JIT.object({ id: JIT.string(), name: JIT.string() }),
  { id: "id" },
);

class User extends UserBase {}

const user = User.create({ id: "u_1", name: "Ada" });
user.identity; // "u_1"
```

DDD lifecycle capabilities resolve their canonical fields before the class is
compiled. Missing fields are injected, compatible fields are reused,
augmentable fields are completed, and conflicts fail during declaration:

```ts
const AuditedUser = JIT.ddd
  .entity(JIT.object({ id: JIT.string(), name: JIT.string() }), { id: "id" })
  .extends(JIT.ddd.timestamps(), JIT.ddd.softDelete(), JIT.ddd.versioned());

const user = AuditedUser.create({ id: "u_1", name: "Ada" });
user.createdAt; // Date
user.updatedAt; // null until touch() or an effective update
user.deletedAt; // null until softDelete()
user.version; // 0
```

Those managed fields are required by `hydrate()` and excluded from ordinary
create/update input. `touch()`, `softDelete()`, and `restore()` are specialized
prototype methods with no lifecycle discovery in their hot path.

## Validation policies

A factory already parses its input — defaults and nested Runtime Types come
from that same pass — so `.validate()` does not turn validation on. It chooses
**how a rejection is reported**, and the choice belongs to the artifact rather
than to the call, so the factory's signature says which shape a caller gets.

```ts
const Money = JIT.ddd.valueObject(
  JIT.object({ amount: JIT.number(), currency: JIT.enum(["BRL", "USD"]) }),
).validate({ result: "result" });

const outcome = Money.create({ amount: 10, currency: "BRL" });
outcome.ok === true && outcome.value.amount; // 10
```

| `result` | `create(input)` returns |
| --- | --- |
| `"throw"` (default) | the instance, or throws `JITValidationError` |
| `"result"` | `{ ok: true; value }` or `{ ok: false; error }` |
| `"tuple"` | `[null, value]` or `[error, null]` |

The tuple puts the error first so it destructures the way callers read it.
Pass `error` to build your own, and `create` / `hydrate` to leave one phase on
the built-in throwing path. A class that never calls `.validate()` carries no
policy at all, in the runtime and in the generated module. The policy is a
singleton declaration: after `.validate(...)`, the method is removed from the
fluent type, and a repeated JavaScript call is rejected.

## Domain assertions

An invariant is written in the same condition builder a query filter uses, so
it becomes a comparison in the generated source rather than a callback the
factory keeps.

```ts
const Price = JIT.ddd
  .valueObject(JIT.object({ amount: JIT.number() }))
  .assert((query) => query.gte("amount", 0), { rule: "non-negative" });

try {
  Price.create({ amount: -1 });
} catch (error) {
  (error as { rule?: string }).rule; // "non-negative"
}
```

`DomainAssertionError` carries `rule` and `field` and never the rejected value.
Assertions run after schema validation and before the instance is built, and
report through the factory's result policy — whether a failure throws or comes
back as a value is one decision for the artifact, not one per invariant.

## Cloning

`clone` is a capability, not a default. Copying a Value Object answers nothing
— the value *is* the identity — and copying an Entity produces two objects
claiming to be the same one, which the domain has to decide rather than
inherit.

```ts
const Session = JIT.class(
  JIT.object({ id: JIT.string(), tags: JIT.array(JIT.string()) }),
).extends(JIT.class.clone);

const session = new Session({ id: "s_1", tags: ["a"] });
const copy = session.clone();
copy.tags === session.tags; // false — the state is copied
```

It reuses the shared clone plan; there is no separate clone engine for classes.
An Aggregate Root's copy starts with an empty event queue: the pending events
belong to the transition that raised them, not to a copy of the state.

## Abstract classes

Use `JIT.class.abstract(schema)` for a domain base. Its static factories use
polymorphic `this`, so subclasses receive their own instance type.

```ts
const UserBase = JIT.class.abstract(UserSchema).factories({
  create: "create",
  hydrate: "hydrate",
});

class User extends UserBase {
  greeting() {
    return `Hello ${this.name}`;
  }
}

User.create({ name: "Ada" }).greeting();
```

The abstract base itself cannot create or hydrate an instance.

## Value objects

`JIT.ddd.valueObject(schema)` is a concrete, frozen runtime class with structural
equality and hash code enabled by default.

```ts
const Money = JIT.ddd.valueObject(
  JIT.object({
    amount: JIT.number(),
    currency: JIT.enum(["BRL", "USD"]),
  }),
);

const price = Money.create({ amount: 10, currency: "BRL" });
Object.isFrozen(price); // true
```

## Scalar value objects

A Value Object over a primitive schema is a real runtime object, never a
primitive with methods bolted on. It exposes a readonly `value` and keeps its
scalar form on the wire.

```ts
const Email = JIT.ddd.valueObject(JIT.string().email());
const email = Email.create("ada@example.com");

email.value; // "ada@example.com"
email.equals(Email.hydrate("ada@example.com")); // true
JSON.stringify({ email }); // {"email":"ada@example.com"}
```

Object Value Objects also answer `value`, returning the whole value, so both
shapes read the same way.

A scalar schema with a default infers the creation arity: when the whole input
can be omitted, `create()` takes no argument at all.

```ts
const Slug = JIT.ddd.valueObject(JIT.string().default("generated"));

Slug.create().value; // "generated"
Slug.create("provided").value; // "provided"
```

## Unique identifiers

`JIT.ddd.uniqueIdentifier()` is that scalar Value Object plus identifier
metadata. With no argument it is a UUID string with a creation default:

```ts
const UserId = JIT.ddd.uniqueIdentifier();

UserId.create().value; // a generated UUID
UserId.hydrate("7f8f4f83-f3c7-4bad-9b73-a3b70f47d761").value; // the persisted one
```

Pass a schema for any other identifier representation:

```ts
const TicketId = JIT.ddd.uniqueIdentifier(JIT.int().positive());
TicketId.create(42).value; // 42
```

The metadata means *identifier-like*, not *the identity of this entity*.
`entity` and `aggregateRoot` infer their identity field only when exactly one
field carries it; zero candidates and several candidates are both rejected,
because an entity may legitimately hold another aggregate's id. Explicit
`{ id: "..." }` always wins.

```ts
const UserId2 = JIT.ddd.uniqueIdentifier();
const UserBase2 = JIT.ddd.abstract.entity(
  JIT.object({ id: UserId2, name: JIT.string() }),
);

class User2 extends UserBase2 {}

User2.create({ name: "Ada" }).id.value; // generated, id omitted at the boundary
```

### Boundary representations

Four representations, and they are not interchangeable:

| Representation | What it is |
| --- | --- |
| Create input | the scalar the boundary accepts; defaults may be omitted |
| Hydrate input | the complete persisted scalar; defaults are never regenerated |
| Runtime | the wrapper object, with `value`, `equals()` and `hashCode()` |
| Wire | the scalar again — `JSON.stringify` never emits `{ "value": ... }` |

Nested Runtime Types accept their **wire** representation and are materialized
by the compiled validator at each known field and array element, so a wrapper
instance is not what a factory takes:

```ts
const OrderBase = JIT.ddd.abstract.entity(
  JIT.object({ id: JIT.ddd.uniqueIdentifier(), tags: JIT.array(UserId) }),
);

class Order extends OrderBase {}

const order = Order.hydrate({
  id: "7f8f4f83-f3c7-4bad-9b73-a3b70f47d761",
  tags: ["f63ca4d3-2b8f-49e6-80ff-0cedaf1e6504"],
});

order.tags[0].value; // materialized from the persisted scalar
```

Passing an already-built `UserId` is rejected on purpose. One boundary
representation keeps `create`, `hydrate`, JSON and AOT saying the same thing,
and avoids an `instanceof` test per field that a generated class in another
module would fail anyway. Reach for `.value` when composing.

## Entities

`JIT.ddd.entity(schema, { id })` creates a concrete factory-first Runtime Type.
Use `JIT.ddd.abstract.entity(...)` for a base that cannot itself be created.
Identity is intentionally distinct from structural equality.

```ts
const UserBase = JIT.ddd.abstract.entity(
  JIT.object({ id: JIT.string(), name: JIT.string() }),
  { id: "id" },
);

class User extends UserBase {}

User.create({ id: "u_1", name: "Ada" }).sameIdentity(
  User.create({ id: "u_1", name: "Grace" }),
); // true
```

## Domain events

`JIT.ddd.domainEvent(type, { payload, version })` creates a frozen class whose
schema contains `id`, literal `type`, literal `version`, `occurredAt`, and the
validated payload. Creation accepts only the payload; id and time are resolved
by defaults.

```ts
const OrderConfirmed = JIT.ddd.domainEvent("order.confirmed", {
  payload: JIT.object({ orderId: JIT.string().min(1) }),
  version: 1,
});

const event = OrderConfirmed.create({ orderId: "o_1" });

event.type; // "order.confirmed"
event.version; // 1
event.payload.orderId; // "o_1"
event["~event"].type; // "order.confirmed"
```

## Aggregate roots

`JIT.ddd.aggregateRoot(schema, { id })` creates a concrete aggregate. Use
`JIT.ddd.abstract.aggregateRoot(...)` for a base with identity, an ordered
pending-event queue, and a compiled in-place `update()`.
Subclass methods express the domain transition, then raise the event that
describes it. Readonly schema fields remain unavailable to `update()`.

```ts
const OrderBase = JIT.ddd.abstract.aggregateRoot(
  JIT.object({
    id: JIT.string().readonly(),
    status: JIT.enum(["draft", "confirmed"]),
  }),
  { id: "id" },
);

class Order extends OrderBase {
  confirm() {
    this.update({ status: "confirmed" });
    this.raise({ type: "order.confirmed" });
  }
}

const order = Order.create({ id: "o_1", status: "draft" });
order.confirm();
order.pullEvents(); // [{ type: "order.confirmed" }]
```

`peekEvents()` returns a snapshot without clearing it. `pullEvents()` returns
the queued events in insertion order and resets the queue.

## AOT

Runtime classes are AOT artifacts too. Pass a class to `AOT.generate()` and
the generated module contains a plain specialized class: validation,
construction, selected capabilities, and aggregate event storage are emitted
locally, with no JIT runtime import. Generated Domain Events preserve
`create(payload)` and `hydrate(state)`; direct construction and `hydrate()` use
the complete persisted event envelope. Value Objects, Entities, Aggregate
Roots, and Domain Events are factory-only by default.

A built-in capability is fully reconstructive. An application method is an
ordinary JavaScript runtime binding, not a reconstructive source artifact.
Standalone AOT therefore **skips the complete class with a reason** naming the
member; it never silently drops a method and never serializes one through
`Function#toString`. Moving function text would discard its lexical environment
and can silently change behavior. Supporting application methods in a future
AOT release requires a declarative method IR or an explicit external-module
binding contract.

`pnpm bench:validate` measured a custom prototype call at 5.76 ns against 5.44
ns for its handwritten class equivalent on Node 22.17.1 / Ryzen 7 5800H. Both
sampled about 6.1 bytes per call: there is no runtime extension dispatcher.
Custom-method AOT is intentionally not benchmarked because generation rejects
that artifact instead of reconstructing it unsafely.

Everything on this page reaches the generated module: the construction token,
the scalar wrapper with its `value` accessor and scalar wire form, the nested
identifier classes co-emitted beside the entity that materializes them, the
result shaping, the error construction, each assertion as a comparison, and
`clone`. A callback that cannot be reconstructed — a custom error factory
built over a captured value, for instance — **skips the artifact with a
reason** rather than generating a module whose failures differ from the
runtime's.
