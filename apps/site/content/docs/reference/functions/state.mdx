`JIT.state` groups operations that describe how application state evolves:

| Operation | Purpose |
| --- | --- |
| `update` | Schema-specialized immutable update with structural sharing |
| `patch.apply` | Apply the canonical deep-partial update contract |
| `patch.merge` | Apply JSON Merge Patch semantics |
| `patch.json` | Apply RFC 6902 operations |
| `collection` | Mutate a collection immutably through a planned access path |
| `derive` | Memoize a computation on the fields it actually reads |
| `reconcile` | Compare keyed collection snapshots with selective sinks |
| `watch` | Compile stateless collection change detection |

```ts
const User = JIT.object({ id: JIT.number(), name: JIT.string() });
const rename = JIT.state.update(User);

const before = { id: 1, name: "Ada" };
const after = rename(before, { name: "Grace" });
```

The namespace does not use a Proxy-based draft runtime to discover shape.
Operations compile from the schema, delay allocation until a semantic change
is known, and preserve references for unchanged branches.

`collection` extends that to a collection: the operation says what should
happen to a row, and the collection's declared facts decide how that row is
reached.

```ts
const Members = JIT.array(User).keyed("id");
const renameMember = JIT.state
  .collection(Members)
  .updateByKey({ key: "id", patch: { name: JIT.cqrs.param("name") } });

renameMember([{ id: 1, name: "Ada" }], { key: 1, name: "Grace" });
renameMember.explain().physical.strategy; // "CachedIndexLookup"
```

## Derived state

Memoization normally asks whether the input object changed. Any immutable
update produces a new object, so a selector over `user.name` is invalidated by
a change to `cart.items` it never reads. `derive` declares what a computation
reads, so its memo asks the narrower question — and given a mutation's change
mask, answers it without reading the state at all.

```ts
const AppState = JIT.object({
  user: JIT.object({ name: JIT.string(), status: JIT.string() }),
  cart: JIT.object({ items: JIT.number() }),
});
const selectHeader = JIT.state.derive(AppState).select("user.name", "user.status").memo();

const state = { user: { name: "Ada", status: "active" }, cart: { items: 2 } };
const header = selectHeader(state);
selectHeader({ ...state, cart: { items: 3 } }) === header; // true
```

Dependencies are inferred from the selection, so there is no `dependsOn` list
to keep in sync. Scalars are compared with `!==` and structural fields with the
schema's own equality; the whole state is never compared.

The optional second argument is a change mask, normally the `changed` channel
of a mutation result. It must describe the transition from the state the
selector last saw. Both sides report their layout, so
`selectHeader.accepts(mutate.layout())` says whether the two agree on what a
bit means.

See [Update](./update), [Patch](./patch),
[Collection mutations](./update#collection-mutations), [Reconcile](./reconcile),
and [Watch](./watch) for the individual contracts.

Stateful aggregate-owned collection tracking is intentionally under
`JIT.ddd.watchedList(...)`; it is not duplicated under `JIT.state`.
