## Query a collection schema

```ts
const Users = JIT.array(User);

const findAdmins = JIT.query(Users)
  .filter((q) => q.eq("role", "admin"))
  .select("id", "name");

findAdmins(users);
```

Predicates build a typed query AST. They are not generic per-item callbacks;
the compiler fuses field reads, comparisons and projection into generated
loops.

## Parameters

```ts
const byRole = JIT.query(Users)
  .params({ role: JIT.string() })
  .filter((q, params) => q.eq("role", params.role));

byRole(users, { role: "member" });
```

Parameters keep one compiled function reusable across values and prevent
constants from being accidentally baked into shared cache entries.

## param

`JIT.param(name)` creates a typed parameter reference for APIs such as
parameterized update patches. Query `.params()` normally provides references
through its callback.

## const

`JIT.const(value)` marks an intentional literal query value. The condition
builder also exposes `q.constant(value)`.

## Operators

Incremental operators include `filter`, `select`, `flatMap`, `take`, `drop`,
`takeWhile`, `dropWhile`, `unique`, `chunk`, `window`, `pairwise`, `scan` and
`groupAdjacentBy`. Global operators such as `orderBy`, arbitrary `groupBy` and
some keyed outputs require materialization.

Mutation outputs are explicit:

```ts
const deactivateAdmins = JIT.query(Users)
  .filter((q) => q.eq("role", "admin"))
  .update({ active: false });
```

Aggregates include `count`, `sum`, `avg`, `min` and `max`.

## Output backends

| Backend                | Result               | Best use                                    |
| ---------------------- | -------------------- | ------------------------------------------- |
| the builder itself     | eager result         | normal arrays and aggregates                |
| `.to.iterator()`       | generator            | early stop and pull consumption             |
| `.to.asyncIterator()`  | async generator      | async pipelines                             |
| `.to.visitor()`        | direct callback sink | highest throughput without iterator objects |
| `.lazy()`              | generator            | generator-first chain                       |

```ts
const visit = JIT.query(Users)
  .filter((q) => q.eq("active", true))
  .to.visitor();

visit(users, (user) => consume(user));
```

## Explain

```ts
const plan = JIT.query(Users)
  .filter((q) => q.gt("score", 10))
  .orderBy("score", "desc")
  .explain("generator");
```

`explain()` reports fused stages and materialization barriers. Check it when a
pipeline expected to stream starts retaining the complete input.

## Binary target

Passing a binary rowset or binary array compiles byte/column scans instead of
hydrated object loops. Only supported predicates, projections and aggregates
are available on that builder.

More operator examples are in [queries](/docs/runtime/queries) and [lazy
execution](/docs/runtime/lazy-execution).
## CQRS

`JIT.cqrs.query(Model)` is a semantic facade over the existing compiled query
IR. It supports `where`, `select`, `orderBy`, `limit`, typed `params`, and a
portable `~query` descriptor; it does not execute a database query itself.
Successive `where` calls are combined with logical AND in both execution and
the portable descriptor. Successive `params` calls accumulate their declared
shape, and `select` narrows the callable result type to the projected fields.
The static CQRS facade is declarative: filters run before ordering, projection,
and limit regardless of chain assembly order. Repeated `select`/`orderBy` use
the last declaration, while repeated limits use the smallest bound; runtime,
AOT, and `~query` share that canonical form.

```ts
const ActiveUsers = JIT.cqrs
  .query(JIT.object({ id: JIT.string(), active: JIT.boolean() }))
  .where((q) => q.eq("active", true))
  .select("id");

ActiveUsers([{ id: "u_1", active: true }]); // [{ id: "u_1" }]
```

`JIT.cqrs.input(Model, options)` declares permitted external filters, sorting,
and offset pagination. `JIT.cqrs.parse(definition)` normalizes input into the
portable filter representation; configured fields and operators are rejected
before a backend adapter sees them.

`filter: { field: true }` is the equality shorthand and accepts only a direct
value. Declare an operator list such as `filter: { age: ["gte", "lte"] }` to
accept operator objects. Top-level arrays, unknown request keys, malformed or
repeated sort/select fields, undeclared fields, and undeclared operators are
rejected identically by runtime and AOT parsers. Offset pagination also rejects
page/limit combinations whose computed offset is not a safe integer.

Cursor pagination uses an opaque compound tuple and always fixes the ordering
to its declared `by` fields. A request may provide exactly one of `after` or
`before`; arbitrary ordering is rejected so a cursor cannot drift between
pages.

Use `limits` to bound untrusted request complexity before it reaches an
adapter. `maxConditions` limits normalized filter operations and
`maxSortFields` limits comma-separated ordering fields; both are enforced by
the generated parser.

Set `select: true` to permit sparse fieldsets such as `fields=id,name`. The
parser checks every selected field against the model schema and can bound the
fieldset with `limits.maxSelectFields`.

Nested filter paths use an explicit dotted key and are normalized as a path in
the standard request: `filter: { "profile.age": { $gte: 18 } }` becomes a
condition with `path: ["profile", "age"]`. The parser validates every segment
against the declared model before an adapter receives it.

```ts
const Users = JIT.object({ id: JIT.string(), createdAt: JIT.string() });
const ListUsers = JIT.cqrs.input(Users, {
  pagination: {
    type: "cursor",
    by: ["createdAt", "id"],
    defaultLimit: 20,
    maxLimit: 100,
  },
});

const parseListUsers = JIT.cqrs.parse(ListUsers);
// parseListUsers({ after: opaqueCursor, limit: 10 })
```
