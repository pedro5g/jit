## Query a collection schema

```ts
const Users = JIT.array(User);

const findAdmins = JIT.query(Users)
  .filter((q) => q.eq("role", "admin"))
  .select("id", "name");

findAdmins(users);
```

Predicates build a typed query AST. They are not generic per-item callbacks;
the compiler fuses field reads, comparisons and projection into generated
loops.

## Parameters

```ts
const byRole = JIT.query(Users)
  .params({ role: JIT.string() })
  .filter((q, params) => q.eq("role", params.role));

byRole(users, { role: "member" });
```

Parameters keep one compiled function reusable across values and prevent
constants from being accidentally baked into shared cache entries.

## param

`JIT.param(name)` creates a typed parameter reference for APIs such as
parameterized update patches. Query `.params()` normally provides references
through its callback.

## const

`JIT.const(value)` marks an intentional literal query value. The condition
builder also exposes `q.constant(value)`.

## Operators

Incremental operators include `filter`, `select`, `flatMap`, `take`, `drop`,
`takeWhile`, `dropWhile`, `unique`, `distinct`, `chunk`, `window`, `pairwise`, `scan` and
`groupAdjacentBy`. Global operators such as `orderBy`, arbitrary `groupBy` and
some keyed outputs require materialization.

Mutation outputs are explicit:

```ts
const deactivateAdmins = JIT.query(Users)
  .filter((q) => q.eq("role", "admin"))
  .update({ active: false });
```

Aggregates include `count`, `sum`, `avg`, `min` and `max`.

`distinct()` keeps the first structurally equal complete row.
`distinct("tenantId", "id")` keeps the first compound key without allocating a
tuple or string key per item. Matching `.ordered(key)` facts select adjacent
comparison and avoid the key table.

## Output backends

| Backend               | Result               | Best use                                    |
| --------------------- | -------------------- | ------------------------------------------- |
| the builder itself    | eager result         | normal arrays and aggregates                |
| `.to.iterator()`      | generator            | early stop and pull consumption             |
| `.to.asyncIterator()` | async generator      | async pipelines                             |
| `.to.visitor()`       | direct callback sink | highest throughput without iterator objects |
| `.lazy()`             | generator            | generator-first chain                       |

```ts
const visit = JIT.query(Users)
  .filter((q) => q.eq("active", true))
  .to.visitor();

visit(users, (user) => consume(user));
```

## Composite aggregate

`aggregate({...})` answers several reductions from one pass, with one
accumulator per field and no intermediate array.

```ts
const Order = JIT.object({ id: JIT.number(), total: JIT.number() });
const Orders = JIT.array(Order);

const summary = JIT.cqrs
  .query(Orders)
  .where((q) => q.gt("total", 10))
  .aggregate({
    count: JIT.cqrs.count(),
    revenue: JIT.cqrs.sum("total"),
    average: JIT.cqrs.avg("total"),
  });

console.log(
  summary([
    { id: 1, total: 50 },
    { id: 2, total: 5 },
  ]),
);
```

The reductions are `JIT.cqrs.count()`, `.sum(key)`, `.avg(key)`, `.min(key)`
and `.max(key)`. `count` and `sum` are `number`; `avg`, `min` and `max` are
`number | undefined`, because an empty pass has no answer for them — never
`NaN` and never `Infinity`.

Declaration order is the result key order and the emission order, so the same
declaration always produces the same source. A composite reduces the whole pass
to one answer, so it cannot be combined with `select`, `orderBy`, scalar
aggregates, terminals or mutations.

### Grouped

`groupBy` is the one collector it composes with. Each group gets its own
accumulator and no group array is ever built.

```ts
const Order = JIT.object({ customerId: JIT.string(), total: JIT.number() });

const perCustomer = JIT.cqrs
  .query(JIT.array(Order))
  .groupBy("customerId")
  .aggregate({ count: JIT.cqrs.count(), total: JIT.cqrs.sum("total") });

console.log(
  perCustomer([
    { customerId: "c1", total: 100 },
    { customerId: "c1", total: 50 },
    { customerId: "c2", total: 25 },
  ]),
);
```

Measured on 10 000 rows in 250 groups: 99.27 µs and 36.8 kB against 216.07 µs
and 298.7 kB for grouping into arrays and reducing them. A grouped average
costs more — it routes accumulation through a `Map` and adds one pass over the
groups — so ask for `count` and `sum` if that pass matters.

`keyed` is rejected: one row per key leaves nothing to reduce.

## Joins

`JIT.cqrs.query(Left).join(Right, kind).on(leftKey, rightKey)` compiles an
`inner`, `left`, `semi` or `anti` relation. The default kind is `inner`.

```ts
const Order = JIT.object({ id: JIT.number(), customerId: JIT.string() });
const Customer = JIT.object({ id: JIT.string(), name: JIT.string() });

const joinOrders = JIT.cqrs
  .query(Order)
  .join(JIT.array(Customer).keyed("id"))
  .on("customerId", "id");

console.log(
  joinOrders([{ id: 1, customerId: "c1" }], [{ id: "c1", name: "Ada" }]),
);
```

The caller never names an algorithm. A keyed right collection selects an
indexed join and reuses its per-array cache; otherwise the generated function
builds one right-side hash index. Compatible ordered facts on both inputs select
a merge join with no index allocation. `join.explain()` reports that private
choice, while `join["~query"]` carries only portable semantic data.

## Terminal sinks

Four terminals answer from inside the loop instead of collecting a result.

| Terminal      | Result                | Stops at                    |
| ------------- | --------------------- | --------------------------- |
| `first()`     | the row, or undefined | the first matching row      |
| `findIndex()` | its index, or `-1`    | the first matching row      |
| `some()`      | boolean               | the first matching row      |
| `every()`     | boolean               | the first row that does not |

```ts
const Users = JIT.array(
  JIT.object({ id: JIT.number(), active: JIT.boolean() }),
);
const users = [
  { id: 1, active: false },
  { id: 2, active: true },
];

const firstActive = JIT.cqrs
  .query(Users)
  .where((q) => q.eq("active", true))
  .first();
const anyActive = JIT.cqrs
  .query(Users)
  .where((q) => q.eq("active", true))
  .some();

console.log(firstActive(users), anyActive(users));
```

The filters are the predicate; the terminal decides how the pass ends. There is
no separate `find` or `firstOrUndefined` — the predicate already lives in
`where`, and `first()` already returns `undefined` when nothing matches.

A terminal has to answer in one pass, so it cannot be combined with `unique`,
`keyed`, `groupBy`, `orderBy`, aggregates or mutations, and it cannot feed
`to.iterator()`, `to.visitor()` or `lazy()`. `select` is allowed before `first`
and rejected before the scalar terminals, where no row is built.

```ts
const Users = JIT.array(
  JIT.object({ id: JIT.number(), active: JIT.boolean() }),
);

try {
  JIT.cqrs.query(Users).orderBy("id").first()([]);
} catch (error) {
  console.log((error as Error).message);
}
```

## Explain

```ts
const plan = JIT.query(Users)
  .filter((q) => q.gt("score", 10))
  .orderBy("score", "desc")
  .explain("generator");
```

`explain()` reports fused stages and materialization barriers. Check it when a
pipeline expected to stream starts retaining the complete input.

### Access paths

For the eager backend it also reports the access path chosen from the
collection's facts. The declaration never changes; the facts do.

```ts
const User = JIT.object({ id: JIT.number(), name: JIT.string() });

const keyed = JIT.cqrs
  .query(JIT.array(User).keyed("id"))
  .where((q) => q.eq("id", 1))
  .first();
const ordered = JIT.cqrs
  .query(JIT.array(User).ordered("id", "asc").uniqueBy("id"))
  .where((q) => q.eq("id", 1))
  .first();
const plain = JIT.cqrs
  .query(JIT.array(User))
  .where((q) => q.eq("id", 1))
  .first();

console.log(keyed.explain().physical?.strategy);
console.log(ordered.explain().physical?.strategy);
console.log(plain.explain().physical?.strategy);
```

| Facts on the collection       | Strategy            | Cost       |
| ----------------------------- | ------------------- | ---------- |
| `.keyed(key)`                 | `CachedIndexLookup` | `O(1)`     |
| `.ordered(key, dir)` + unique | `BinarySearch`      | `O(log n)` |
| none of the above             | `EarlyExitScan`     | `O(k)`     |

Only a single `eq` filter ending in `first()` or `some()` is lifted off a scan.
An index maps a key to a row rather than a position, so `findIndex()` stays a
scan, and `every()` has to see every row by definition.

A cached index is built once per array and reused. It repays across repeated
lookups on the same array and loses badly when the array is rebuilt per call —
declare `.ordered()` instead in that case, since a binary search allocates
nothing. Measured numbers are in
[physical query planning](https://github.com/pedro5g/jit/blob/main/docs/features/physical-query-planning.md).

## Binary target

Passing a binary rowset or binary array compiles byte/column scans instead of
hydrated object loops. Only supported predicates, projections and aggregates
are available on that builder.

More operator examples are in [queries](/docs/runtime/queries) and [lazy
execution](/docs/runtime/lazy-execution).

## CQRS

`JIT.cqrs.query(Model)` is a semantic facade over the existing compiled query
IR. It supports `where`, `select`, `orderBy`, `limit`, typed `params`, and a
portable `~query` descriptor; it does not execute a database query itself.
Successive `where` calls are combined with logical AND in both execution and
the portable descriptor. Successive `params` calls accumulate their declared
shape, and `select` narrows the callable result type to the projected fields.
The static CQRS facade is declarative: filters run before ordering, projection,
and limit regardless of chain assembly order. Repeated `select`/`orderBy` use
the last declaration, while repeated limits use the smallest bound; runtime,
AOT, and `~query` share that canonical form.

```ts
const ActiveUsers = JIT.cqrs
  .query(JIT.object({ id: JIT.string(), active: JIT.boolean() }))
  .where((q) => q.eq("active", true))
  .select("id");

ActiveUsers([{ id: "u_1", active: true }]); // [{ id: "u_1" }]
```

`JIT.cqrs.input(Model, options)` declares permitted external filters, sorting,
and offset pagination. `JIT.cqrs.parse(definition)` normalizes input into the
portable filter representation; configured fields and operators are rejected
before a backend adapter sees them.

`filter: { field: true }` is the equality shorthand and accepts only a direct
value. Declare an operator list such as `filter: { age: ["gte", "lte"] }` to
accept operator objects. Top-level arrays, unknown request keys, malformed or
repeated sort/select fields, undeclared fields, and undeclared operators are
rejected identically by runtime and AOT parsers. Offset pagination also rejects
page/limit combinations whose computed offset is not a safe integer.

Cursor pagination uses an opaque compound tuple and always fixes the ordering
to its declared `by` fields. A request may provide exactly one of `after` or
`before`; arbitrary ordering is rejected so a cursor cannot drift between
pages.

Use `limits` to bound untrusted request complexity before it reaches an
adapter. `maxConditions` limits normalized filter operations and
`maxSortFields` limits comma-separated ordering fields; both are enforced by
the generated parser.

Set `select: true` to permit sparse fieldsets such as `fields=id,name`. The
parser checks every selected field against the model schema and can bound the
fieldset with `limits.maxSelectFields`.

Nested filter paths use an explicit dotted key and are normalized as a path in
the standard request: `filter: { "profile.age": { $gte: 18 } }` becomes a
condition with `path: ["profile", "age"]`. The parser validates every segment
against the declared model before an adapter receives it.

```ts
const Users = JIT.object({ id: JIT.string(), createdAt: JIT.string() });
const ListUsers = JIT.cqrs.input(Users, {
  pagination: {
    type: "cursor",
    by: ["createdAt", "id"],
    defaultLimit: 20,
    maxLimit: 100,
  },
});

const parseListUsers = JIT.cqrs.parse(ListUsers);
// parseListUsers({ after: opaqueCursor, limit: 10 })
```
