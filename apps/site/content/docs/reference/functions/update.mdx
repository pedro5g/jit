## Compile an updater

```ts
const updateUser = JIT.state.update(User);

const next = updateUser(current, {
  profile: { name: "Grace" },
});
```

Only changed branches are allocated. Unchanged children retain identity:

```ts
next !== current;
next.settings === current.settings;
```

An immediate overload is available for one-off work:

```ts
const next = JIT.state.update(User, current, { active: false });
```

Compile and reuse the function for repeated updates.

## Draft recipes

```ts
const next = updateUser(current, (draft) => {
  draft.profile.name = "Grace";
  draft.stats.logins = 42;
});
```

The draft is a write recorder, not the original object. Reads from the draft
do not provide current values, so compute dependent values outside the recipe.
Recipes are convenient for typed paths; plain patches have lower setup cost in
very hot loops.

## Parameterized patches

```ts
const setRole = JIT.state.update(User)
  .patch({
    role: JIT.cqrs.param("role"),
  })
  .compile();

const admin = setRole(user, { role: "admin" });
```

The patch shape is known before the call, so it lowers to a mutation plan
rather than to a patch object: normalized writes, a read/write set, and a copy
tree that says which levels have to be rebuilt. The generated function reads
each written field once, compares, and only then allocates — one object per
changed level, unchanged branches kept by reference, and the original value
returned when nothing changed. Writes to one parent rebuild it once, and a
write a later write overwrites is not emitted at all.

A path is specialized only when the generic update would *assign* its leaf: a
primitive, an optional or nullable primitive, or a date. An object, array, map,
set or union leaf is *merged* by the deep-partial update, so those keep running
through it — a declared patch never changes meaning in order to become faster.

```ts
const declared = JIT.state.update(User).patch({ role: JIT.cqrs.param("role") });

declared.explain();
// { strategy: "specialized", reads: ["role"], writes: ["role"], params: ["role"] }
```

On a three-level object a declared patch runs in about half the time of the
generic update it specializes, and returns the original value in about 10 ns
when nothing changed.

## Collection mutations

`JIT.state.collection(Users)` mutates a collection immutably. The operation is
semantic — update this key, remove it, upsert it — and the algorithm that finds
the row comes from the collection's declared facts: a cached index for
`.keyed()`, a binary search for `.ordered()` and unique, an early-exit scan
otherwise. `explain().physical` reports which one was chosen.

```ts
const Members = JIT.array(User).keyed("id");
const renameMember = JIT.state
  .collection(Members)
  .updateByKey({ key: "id", patch: { name: JIT.cqrs.param("name") } });

const members = [{ id: "u_1", name: "Ada", active: true, role: "admin" }];
renameMember(members, { key: "u_1", name: "Grace" });
renameMember.explain().physical.strategy; // "CachedIndexLookup"
```

`removeByKey`, `upsert`, `append` and `prepend` are compiled the same way.
`updateWhere` and `removeWhere` select rows with the shared query condition
rather than by identity; a predicate that can match several rows visits every
row, while one equality over a key the collection declares unique is lifted
onto the same access path identity uses.
Nothing is copied before the decision: a missing key and a row that did not
change both return the original array, and removal fills one array of length
`n - 1` with indexed loops rather than calling `filter`.

Reaching the row can be `O(1)` or `O(log n)`; rebuilding the array is `O(n)`
whatever found it, which `explain().copy` reports separately. An ordered
`upsert` inserts at the position the search reported, so the collection stays
ordered.

Writing the identity key or the ordering key through `updateByKey` is refused:
both would leave the collection claiming a fact that is no longer true. Remove
and insert the row instead.

## Reactive mode

```ts
const users = JIT.state.update(State).reactive(initialState, {
  schedule: "microtask",
});

const unsubscribe = users.watch("profile.name", (event) => {
  console.log(event.previous, event.value);
});

users.update({ profile: { name: "Grace" } });
unsubscribe();
```

Reactive controllers support tuple or dot-path watchers, selectors, batching,
custom equality, sync/microtask/custom scheduling, global subscriptions and
explicit disposal. The expensive diff array is computed lazily only if a
subscriber reads `event.changes`. Read [reactive
updates](/docs/runtime/reactive-updates) for the complete event model.

## Readonly schemas

Updates reject readonly branches. Create a mutable command/input schema for
write operations and expose a readonly view where mutation must be prohibited.

## Performance

The compiler knows every path and emits direct assignments. Structural sharing
reduces allocations compared with cloning the entire value. Reactive mode adds
subscription bookkeeping; use the plain updater when no observers exist.

## AOT

Plain compiled updates and parameterized patch functions can be emitted as
standalone functions. A process-local reactive controller remains a runtime
state owner and is constructed around the compiled updater.
