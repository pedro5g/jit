---
title: DTO schemas
description: Mark inbound and outbound contracts, then compose only the validation, mapping, and transport artifacts they need.
---

A data transfer object is a boundary contract, not a domain entity with fewer
methods. `JIT.dto(schema)` adds boundary metadata to an ordinary schema; it
does not create another compiler or operation facade. Compose that schema with
the same capabilities used everywhere else:

- `JIT.validate.parse` or `JIT.validate.safeParse` for already-decoded input;
- `JIT.json.parse(dto).validate()` for JSON text;
- `JIT.map` or `JIT.map.many` for outbound whitelisting;
- `JIT.json`, `JIT.binary`, masking, and hashing when the boundary needs them.

This design follows the usual DTO goals documented by [Microsoft
Learn](https://learn.microsoft.com/en-us/aspnet/web-api/overview/data/using-web-api-with-entity-framework/part-5):
hide fields, reduce payloads, flatten graphs, avoid circular references and
decouple service/database shapes. It also follows the [OWASP mass-assignment
guidance](https://cheatsheetseries.owasp.org/cheatsheets/Mass_Assignment_Cheat_Sheet.html):
bind only explicitly allowed fields instead of passing an entity directly to a
write operation.

## Inbound DTO

```ts
import { JIT } from "@jit-compiler/jit/runtime";

const CreateUserDTO = JIT.dto(
  JIT.object({
    name: JIT.string().min(2).max(80),
    email: JIT.string().email(),
  }).strict(),
);

export const parseCreateUser = JIT.validate.parse(CreateUserDTO);
export const safeParseCreateUser = JIT.validate.safeParse(CreateUserDTO);
export const parseCreateUserJson = JIT.json.parse(CreateUserDTO).validate();

const command = parseCreateUser(request.body);
const fromQueue = parseCreateUserJson(message.data);
```

Use `strict()` when unexpected keys should be an error. A loose or stripping
object can be appropriate for forward-compatible clients, but authorization
must never depend on silently ignored fields.

## Outbound DTO

Mapper output is a whitelist by construction: fields absent from the target
schema cannot enter the object, even when they exist on the source entity.

```ts
const UserEntity = JIT.object({
  id: JIT.number().int32(),
  fullName: JIT.string(),
  passwordHash: JIT.string(),
  profile: JIT.object({ city: JIT.string(), internalScore: JIT.number() }),
});

const PublicUserDTO = JIT.dto(
  JIT.object({
    id: JIT.number().int32(),
    name: JIT.string(),
    city: JIT.string(),
  }),
);

const mapping = {
  name: { from: "fullName" },
  city: (user: JIT.Typeof<typeof UserEntity>) => user.profile.city,
} as const;

export const toPublicUser = JIT.map(UserEntity, PublicUserDTO, mapping);
export const toPublicUsers = JIT.map.many(UserEntity, PublicUserDTO, mapping);
export const publicUserJson = JIT.from(UserEntity)
  .map(PublicUserDTO, mapping)
  .to.json();

const publicUser = toPublicUser(entity);
const publicUsers = toPublicUsers(entities);
response.end(publicUserJson(entity));
```

Same-name compatible fields are copied automatically. Renames use `{ from }`,
conversions use `{ from, via }`, computed fields use callbacks, and constants
use `{ default }`. Required target fields that cannot be produced are a
TypeScript error and an `INVALID_MAPPER` runtime error.

`JIT.map.many` is not `sources.map(toPublicUser)`: generated source contains one
indexed loop and inlines every field write. A terminal `.to.json()` can map and
serialize in the same output loop without allocating the mapped collection.

## Capabilities stay explicit

| Need                          | Artifact                                      |
| ----------------------------- | --------------------------------------------- |
| boolean gate                  | `JIT.validate.is(Dto)`                                 |
| throwing validation           | `JIT.validate.parse(Dto)`                              |
| issue result                  | `JIT.validate.safeParse(Dto)`                          |
| validated JSON input          | `JIT.json.parse(Dto).validate()`              |
| specialized JSON output       | `JIT.json.stringify(Dto)`                     |
| binary transport              | `JIT.codec(Dto)` or `JIT.binary.*(Dto)`       |
| one entity to DTO             | `JIT.map(Entity, Dto, mapping)`               |
| entity collection to DTO list | `JIT.map.many(Entity, Dto, mapping)`          |
| explicit artifact object      | `{ parse: JIT.validate.parse(Dto) }` |

There is no DTO-specific operation list. Independent artifacts make unused
capabilities absent from both the value and its TypeScript type.

## Create, update, and view variants

DTO variants are normal immutable schema transforms. There is no second class
hierarchy or metadata reflection layer.

```ts
const UserFields = JIT.object({
  id: JIT.number().int32(),
  name: JIT.string().min(2),
  email: JIT.string().email(),
  role: JIT.string(),
});

const CreateUserDTO = JIT.dto(UserFields.omit("id", "role"));
const PatchUserDTO = JIT.dto(UserFields.pick("name", "email").partial());
const UserViewDTO = JIT.dto(UserFields.omit("role"));

const parseCreate = JIT.validate.parse(CreateUserDTO);
const parsePatch = JIT.validate.parse(PatchUserDTO);
const toView = JIT.map(UserFields, UserViewDTO, {});
```

This is the same role served by `PartialType`, `PickType`, and `OmitType` in
[NestJS mapped types](https://docs.nestjs.com/openapi/mapped-types), but JIT
transforms produce schema AST directly and therefore feed every compiler.

## AOT and tree shaking

Export the exact callable artifacts from a configured `*.jit.ts` entry:

```ts
export const parseCreate = JIT.validate.parse(CreateUserDTO);
export const publicUsersJson = JIT.map
  .many(UserEntity, PublicUserDTO, mapping)
  .to.json();

export const CreateBoundary = {
  is: JIT.validate.is(CreateUserDTO),
  parse: parseCreate,
  fromJSON: JIT.json.parse(CreateUserDTO).validate(),
};
```

AOT lowers direct artifacts and complete grouped ExecutionPlans, emitting only
the declared operations with no JIT runtime import. Self-contained mapper
callbacks can be serialized; generation reports callbacks it cannot safely
reconstruct instead of silently changing behavior.

## Correctness boundaries

`parse` validates untrusted DTO-shaped data. Mapping assumes a typed source and
uses the target schema as its output whitelist. If a callback crosses an
`unknown` or external-library boundary, validate the mapped result explicitly:

```ts
const publicUser = JIT.validate.parse(PublicUserDTO)(toPublicUser(entity));
```

A DTO prevents accidental field exposure and mass assignment, but it does not
authorize the caller. Property-level authorization and business invariants
still belong in the application or domain layer.
