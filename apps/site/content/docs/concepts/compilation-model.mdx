---
title: Compilation model
description: How schemas become specialized runtime JIT or import-free AOT functions.
---

JIT treats a schema as compile-time input. Schema traversal, wrapper resolution,
strategy selection, optimization and source generation happen once; hot calls run
plain JavaScript specialized for one known shape.

```text
JIT builders -> schema AST -> execution plan -> optimizer -> code generator
                                                       -> runtime Function
                                                       -> pure AOT module
```

## Runtime JIT

Runtime operations compile through `globalThis.Function` and are cached by schema
identity and operation plan. External values such as predicates and query constants
are passed as bindings, never interpolated into generated source.

```ts
const parseUser = JIT.json.parse(User).validate();

parseUser.plan;
parseUser.explain();
parseUser.compile(); // optional warm-up; returns the same callable
```

The default cache, cold-compilation configuration and the separate hash/index
caches are covered in [cache, hash and indexes](/docs/runtime/cache-hash-index).

## Build-time AOT

`jit generate` evaluates explicit declarations and writes self-contained ESM, CJS and
declaration files. Generated operations have zero imports from the JIT engine, so the
schema builders and compiler do not ship in the production bundle.

## Why the generated path is fast

- known properties use direct access;
- arrays use indexed loops;
- validators order cheap checks before regex and transforms;
- one execution plan lowers source, validation, query, map, transform, update,
  security, and sink stages together;
- adjacent queries fuse filtering and projection;
- binary rowsets replace string discriminators and booleans with integer codes;
- unused operations are never generated.

Native `JSON.parse` remains a deliberate materialization boundary. JIT runs
the generated validator immediately after it in the same execution callable
rather than assuming a JavaScript token parser would be faster. Read the
[composable execution guide](/docs/runtime/composable-execution) before
interpreting “fused” as “zero allocation”.

Compile cost and execution cost are reported separately in benchmarks. A complicated
optimization is accepted only when the hot-path result justifies it.
